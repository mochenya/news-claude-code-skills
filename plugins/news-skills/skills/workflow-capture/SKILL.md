# 工作流 Markdown 文档生成器

将用户的方案、路线规划或探索成果，转化为结构清晰、可执行、可复用的工作流文档。

核心价值：**方案固化为可复用指导文档**。不是美化排版，而是确保工作流完整可执行。

完整模板：`references/workflow-template.md`

## 工作原则

生成文档前必须理解三件事：

1. **为什么做**：背景、痛点、触发原因
2. **怎么做**：路线、方法、技术栈、工具、约束
3. **解决什么**：预期结果、交付物、成功标准

三要素齐全 → 直接生成。有缺口 → 追问补全。

## 追问策略

遇到以下情况先追问：

- 目标宽泛，缺少具体路线
- 只有方法没有原因或预期结果
- 依赖的技术栈、工具、权限未说明
- 边界不清（能做什么/不能做什么）
- 缺少验证标准

追问原则：一次问 3-5 个聚焦问题，不泛泛而问，能一次问清就不分多轮。

```markdown
还需确认几点：

1. 这个工作流要解决的核心问题是什么？
2. 执行路线中用到哪些技术栈/工具/skill？
3. 做完后怎样算成功？
4. 有哪些明确的边界（能做/不能做）？
5. 验证阶段检查什么？
```

## 用户没有路线时

先提出简短探索路线 → 标注为假设 → 用户确认后再生成最终文档。

## 篇幅控制

- 轻量任务：50-90 行，2-3 阶段
- 标准工作流：90-150 行，3-5 阶段
- 复杂项目：150-200 行，不超过 200 行

每个项目符号 1-2 行，每阶段 2-5 个动作。不写废话，不省关键步骤。

## 生成前检查

确认以下信息（小任务不必全填，但不能省掉影响执行的项）：

- 工作流名称
- 三要素（为什么/怎么做/解决什么）
- 技术栈、工具、skills
- 输入材料与前置条件
- 执行路线与阶段划分
- 边界（范围内/范围外）
- 验证方法与通过标准

## 输出规则

信息足够时，读取 `references/workflow-template.md` 生成最终文档。

- 保持模板章节结构稳定
- 用编号标题和短项目符号，可扫读
- 技术栈/工具用表格
- 不确定但不阻塞的写 `待确认：...`
- 不确定且影响执行的，先问用户
- 不把假设藏在叙述里

## 边界

**可以做：**
- 方案完整时直接生成可复用工作流文档
- 方案有缺口时追问补全再生成
- 用户没路线时先提探索路线供确认
- 对未知项标注待确认

**不可以做：**
- 编造技术细节、工具、权限或指标
- 跳过三要素直接输出
- 输出没有验证阶段的文档
- 把模糊需求包装成确定方案

## 响应流程

1. 提取已知三要素
2. 检查技术栈、工具、边界、验证是否缺失
3. 缺失 → 追问；齐全 → 生成
4. 没有路线 → 先给探索路线让用户确认
5. 读取模板，按复杂度控制行数，生成最终文档
6. 列出剩余 `待确认` 项（没有则不补充）
